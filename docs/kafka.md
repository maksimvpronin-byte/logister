# Kafka между Fluent Bit и Logister

Цепочка локального стенда:

```text
Файлы логов → Fluent Bit → Kafka (logister-ingest, 6 разделов)
                                      ↓
                           Kafka consumer внутри API
                                      ↓
                         Журнал приёма Redis
                                      ↓
                                OpenSearch
```

`docker compose up --build -d` поднимает также Kafka и создаёт входящий топик.
Для стенда с LDAP используйте `./deploy/start-ldap-auth.sh`.
Внутри Docker адрес брокера `kafka:9092`, с хоста — `127.0.0.1:19092`.
Брокер, данные и смещения группы сохраняются в томе `kafka_data`.
Параметры API: `KAFKA_BROKERS`, `KAFKA_TOPIC` (по умолчанию `logister-ingest`),
`KAFKA_GROUP` (по умолчанию `logister`). Без `KAFKA_BROKERS` Kafka input выключен.

Прямые HTTP-адреса приёма сохранены. Для Fluent Bit основным выходом стал Kafka.
В топик передаётся один JSON-объект на сообщение. Используются существующие
правила маршрутизации и ограничения валидации. Поле `stream` явно выбирает поток;
без него выполняется автоматическая маршрутизация.

## Подтверждения и повторная доставка

Consumer читает до 1000 сообщений, сохраняет весь пакет в Redis и только
затем подтверждает Kafka offsets. Автоматическое подтверждение выключено.
При ошибке сохранения либо подтверждения consumer переходит к повторному чтению
с последнего подтверждённого смещения. Идентификаторы `id` / `delivery_id`
сохраняются; при их отсутствии используется `topic + partition + offset`.
Поэтому повтор чтения того же Kafka record не создаёт второй поисковый документ.
Это доставка как минимум один раз с дедупликацией в Logister.

Невалидный JSON, конфликт идентификатора, удалённый/неизвестный поток не пропускаются
молча. Чтение повторяется с ошибкой, видимой администратору. Нужно устранить причину,
например восстановить поток; автоматического пропуска или DLQ сейчас нет.

Показатель «Подтверждено Logister» означает запись в Redis. Отдельный
показатель «Доставлено в потоки» означает подтверждённую запись в OpenSearch.
Нулевой Kafka lag сам по себе не означает, что журнал Redis уже опустел.

## Управление

Администратору доступна панель «Kafka → Logister» и API:

- `GET /api/ingest/kafka`: состояние, lag, сохранённые в Kafka сообщения,
  подтверждённые смещения группы, ошибки, признаки потери данных по retention.
  Массив `partitions` показывает начало и конец доступного диапазона,
  подтверждённое смещение, lag и признак потери диапазона для каждой партиции.
  Метрика `max_partition_lag` в `GET /api/monitoring` показывает отставание
  самой загруженной партиции.
- `PUT /api/ingest/kafka` с `{"paused":true}` / `{"paused":false}`: пауза/возобновление.

Пауза завершается на границе текущего пакета. До `running:false` пакет ещё может
завершаться. После этого клиент выходит из группы; при возобновлении заново
присоединяется и читает с подтверждённых смещений. Пауза сохраняется в PostgreSQL
и переживает перезапуск API. Kafka продолжает принимать сообщения на паузе.
Операторы и технические учётные записи не могут управлять чтением или просматривать
общую статистику Kafka, поскольку топик содержит сообщения разных потоков.

`available` и `committed` вычислены по диапазону сохранённых offsets и меняются
после удаления сегментов по retention. Это не вечные накопительные счётчики.
При ошибке мониторинга интерфейс сохраняет предыдущие значения с предупреждением.

## Нагрузочный тест накопленной очередью

1. Создайте отдельный поток в интерфейсе, например `kafka-benchmark`.
2. Приостановите чтение Kafka и дождитесь состояния «Чтение на паузе».
3. Наполните Kafka, например из каталога `api`:

```sh
go run ./cmd/kafka-load -brokers 127.0.0.1:19092 -stream kafka-benchmark -count 500000 -bytes 512
```

Производитель ограничивает свой буфер и ждёт Kafka; при заполнении буфера он
блокируется, а не пропускает запланированные события. Все отправленные записи
должны получить подтверждение брокера. Текст сообщений содержит случайные данные,
чтобы не создавать нереалистично хорошее сжатие повторяющегося текста.
Вывод содержит requested, acknowledged, failed, bytes и скорость производителя.
Размер `bytes` задаёт текст сообщения; полный JSON больше из-за метаданных.

4. Убедитесь, что очередь Kafka выросла, а счётчик приёма тестового потока ещё нулевой.
5. Возобновите чтение. Измеряйте уменьшение lag, скорость приёма и доставки,
   время до пустых Kafka и Redis, точное число документов в поиске.

Готовый автоматический сценарий с созданием потока, проверкой сохранения паузы
после перезапуска API, наполнением и точной сверкой поиска:

```sh
python3 deploy/tests/kafka_backlog.py --count 250000
```

Он использует локальный LDAP-стенд, оставляет тестовый поток для проверки,
возвращает прежнее состояние паузы и сохраняет отчёт в `graphify-out/kafka-test`.
Сначала завершает наполнение и только затем запускает чтение: скорость
производителя не ограничивает измеряемую скорость обработки Logister.

## Ограничения локального стенда

Один брокер KRaft, replication factor 1, plaintext только на loopback хоста
и внутренней Docker-сети. Это локальная лаборатория, без отказоустойчивости брокера.
Retention — 24 часа и примерно 2 ГБ на топик (лимит задан на каждый из 6 разделов),
с сегментами 32 МиБ. Лимит проверяется по закрытым сегментам и не является точным
ограничением дискового места. Retention может удалить непрочитанные записи:
перед большими тестами нужно проверить бюджет диска и срок хранения.

Kafka позволяет накопить нагрузку и разделить приём/обработку, но сама по себе
не ускоряет SQL-операции и индексацию Logister.

Документация: [Kafka output Fluent Bit](https://docs.fluentbit.io/manual/data-pipeline/outputs/kafka),
[официальный Docker-пример Kafka 3.9.1](https://github.com/apache/kafka/blob/3.9.1/docker/examples/docker-compose-files/single-node/plaintext/docker-compose.yml),
[franz-go](https://pkg.go.dev/github.com/twmb/franz-go/pkg/kgo).

Для служебной метки Kafka-выхода Fluent Bit зарезервировано поле
`__logister_kafka_timestamp`: consumer удаляет его до проверки идентичности
и сохранения пользовательского payload. Служебное время повторного чтения
не меняет идентичность события. Для перехода с первого Kafka-конфига поддержана
его прежняя числовая метка `@timestamp` в envelope с `delivery_id`, когда
Kafka message key совпадает с этим `delivery_id`. Если такой
документ уже был сохранён, совместимость проверяется по сохранённому исходному
payload и обоим хешам, затем хеш нормализуется. Изменение самого сообщения
по-прежнему вызывает конфликт идентификатора.

При выходе подтверждённого смещения за диапазон Kafka consumer останавливается
с ошибкой `OffsetOutOfRange`, вместо автоматического перескока через удалённые
данные. При самом первом подключении группы чтение начинается с начала
сохранённого диапазона. Без старых смещений невозможно восстановить уже удалённые
брокером сообщения.

## Настройка производительности

API по умолчанию готовит сообщения в 4 обработчика, принимает Kafka poll до 1000
записей и разбивает его на части до 10 МиБ. Все части должны быть сохранены перед
подтверждением offsets. `INGEST_WORKERS`, `KAFKA_BATCH_RECORDS`, `KAFKA_BATCH_BYTES`
задают эти параметры. Получение poll и подтверждение offsets остаются последовательными.

Publisher выбирает до 1000 записей / 10 МиБ документов (`PUBLISH_BATCH_BYTES`),
отправляет до 2 bulk параллельно, по 5 МиБ (`BULK_WORKERS`, `BULK_MAX_BYTES`).
Размер bulk включает оценку служебных строк; один oversized документ допускается.
Подтверждение Redis атомарно проверяет аренду и весь префикс; при частичном успехе
в OpenSearch диапазон повторяется с прежними ID.

Бюджет ожидающих тел — 256 МиБ (`INGEST_QUEUE_MAX_BYTES`). При заполнении приём
ждёт до 30 секунд, не подтверждая новые offsets Kafka. Один пакет сверх бюджета
допускается в пустую очередь. Это не лимит всей памяти Redis: ID/hash сохраняются
после публикации, отдельно от тел. Текущий бюджет тел хранится в
`logister:pending-bytes:logs-v2`.

[Реализация, сравнение настроек и проверки на 10 КиБ](audits/ingest-10k-optimized-2026-11-03.md).
### Прямой режим Kafka

В прямом режиме API пишет Kafka-события в OpenSearch и подтверждает смещения
после успешной записи всей порции. Запись требует `translog.durability=request`
и подтверждений всех настроенных копий шарда. MongoDB в режиме replica set
хранит ID, хеш, время документа и назначенное поколение индекса. Тела остаются
в Kafka до обработки. При повторе запись попадает в исходное поколение,
даже если оно уже запечатано. Счётчики приёма и ротация учитывают прямые
поколения отдельно от HTTP; для поиска используется общий read alias.

Для одного API добавьте `-f deploy/docker-compose.kafka-direct.yml` после
основного Compose и, при необходимости, LDAP overlay. Файл инициализирует
одночленный replica set на текущем томе MongoDB. Для кластерного Compose
укажите `KAFKA_DIRECT=true` на всех API. Одновременно запускайте только
экземпляры одного режима в группе. Перед переключением остановите
производителей, дождитесь нулевого Kafka lag и пустого Redis-журнала,
остановите старые потребители, затем запустите новые с той же consumer group.

Для проверки и постепенного ввода используйте отдельный топик. Прямые
поступления используют отдельный реестр ID от HTTP и старого Redis-тракта.
При переключении сохраняйте подтверждённые смещения и исключайте повторы
старых явных ID из прежнего тракта. В режиме Kafka Direct с заданным
`REDIS_URL` HTTP-приём использует Redis. Если `REDIS_URL` отсутствует, API
работает без Redis и принимает события только через Kafka. Для этого режима
используйте [Compose и Ansible для продакшена](../deploy/cluster/README.md).
При отказе OpenSearch Kafka должна вмещать непрочитанный объём по каждой
партиции до восстановления.

Эксперимент `deploy/tests/kafka_direct_profile.py` использует один фиксированный
индекс. Он подходит для измерения транспорта, а штатный прямой режим также
проверяет маршрутизацию, ротацию и устойчивость повторов.

Для сравнения 1/2/4 primary shard на том же Redis pipeline:

```sh
python3 deploy/tests/kafka_shard_matrix.py
```

Сценарий меняет число шардов только у создаваемых тестовых индексов, делает
по два прогона 100 000 × 10 КиБ и восстанавливает настройки API.
`INGEST_PROFILE_BULK=true` временно включает технический журнал времени bulk,
без payload; по умолчанию выключен. Собираются Linux diskstats, PSI и cgroup I/O.
[Результаты и ограничения измерений](audits/ingest-shards-10k-2026-11-03.md).

После локализации ограничения индексации новые managed-индексы создаются с
`OPENSEARCH_SHARDS=2` (диапазон 1–16). Настройка применяется при создании;
для действующего потока используется штатная ротация, старые поколения сохраняются.
`INGEST_PROFILE_STAGES=true` включает раздельные таймеры Kafka, подготовки,
приёма Redis и publisher; по умолчанию выключен, payload не записывается в журнал.
[Локализация, установленное исправление и контрольные тесты](audits/ingest-bottleneck-research-2026-11-03.md).

## Выходной буфер готовых пакетов

`OUTPUT_BUFFER_BYTES=33554432` включает RAM-буфер между Redis и writer OpenSearch.
При пакетах `PUBLISH_BATCH_BYTES=10485760` одновременно подготавливаются до трёх
окон, включая записываемое. Чтение следующего окна перекрывается с записью
предыдущего. Максимум — 8 окон; если помещается меньше двух, используется
последовательный режим. `OUTPUT_BUFFER_BYTES=0` явно отключает предвыборку.
Бюджет относится к телам, не к RSS процесса. Publisher сначала получает длины
тел и выбирает префикс по байтам, затем загружает только выбранные тела. Один
документ сверх лимита допускается ради прогресса; это может превысить бюджет окна.

До успешного ACK тела остаются в Redis. Заполнение RAM-буфера останавливает
читателя; заполнение журнала Redis передаёт обратное давление приёму. Само чтение
в RAM не увеличивает счётчик доставленных сообщений.
[Реализация, ограничения и тесты выходного буфера](audits/output-buffer-2026-11-03.md).

Внутренний CPU-профиль OpenSearch выявил высокую стоимость LZ4-сжатия полного
сохраняемого JSON. Для новых managed-индексов теперь используются
`OPENSEARCH_CODEC=zstd_no_dict` и `OPENSEARCH_CODEC_LEVEL=1` (уровни 1–6).
`OPENSEARCH_CODEC=default` возвращает прежний алгоритм для будущих индексов.
Существующие поколения сохраняют свой codec; переход выполняется ротацией.
[Профили JVM, сравнение codec и ограничения результатов](audits/opensearch-internal-bottleneck-2026-11-03.md).

После успешной проверки точного количества сообщений `kafka_profile.py`,
`kafka_backlog.py`, `ingest_load.py`, `kafka_direct_profile.py` и
`ingest_optimized_faults.py` удаляют данные своего синтетического потока:
индексы OpenSearch и Redis-записи дедупликации. Поток архивируется,
каталог индексов отмечается удалённым; JSON-отчёты и замеры сохраняются.
Неуспешный прогон оставляет данные для диагностики. Retention общего Kafka-топика
не меняется; общие данные Kafka принудительно не очищаются.

Для старых прогонов: `python3 deploy/tests/cleanup_loadtests.py` показывает план,
`python3 deploy/tests/cleanup_loadtests.py --apply` выполняет очистку.
Выбираются только известные синтетические имена с подтверждением в отчётах или
описанием диагностического скрипта. Обычные потоки не выбираются. Очистка
отказывается работать при непустой очереди публикации. Результат сохраняется
в `graphify-out/cleanup/`. Повторное сравнение методик на очищенном стенде:
`python3 deploy/tests/recheck_clean.py`.

Размер текста сообщения в `kafka_profile.py` и `ingest_research.py` по умолчанию
теперь 500 байт. Он задаётся через `--bytes`; JSON-обёртка и метаданные идут сверх
этого размера. Полная индексация message включена независимо от размера теста.
Пример двух прогонов с проверкой длины индексированного текста и автоочисткой:

```sh
python3 deploy/tests/ingest_research.py --label fulltext-500b --shards 2 2 --auto-index --count 100000 --bytes 500 --sample-interval 0.25
```

Для воспроизведения прежних тестов явно укажите `--bytes 10240`. Матрицы,
посвящённые сравнению шардов и кодеков на 10 КиБ, сохраняют свой размер нагрузки.

## Проверка конфигураций и логики

`python3 deploy/tests/configuration_audit.py` сравнивает шесть вариантов на
100 000 сообщениях по 5 КиБ: текущий, последовательная публикация без RAM
предвыборки, один normalizer, один bulk worker, один шард, минимальный вариант.
Второй круг идёт в обратном порядке. `--suite lean` сравнивает текущий вариант
с `INGEST_WORKERS=1 OUTPUT_BUFFER_BYTES=0` по схеме ABBA. Исходные параметры
возвращаются в finally; каждый успешный прогон проверяет полноту индексации и
удаляет свои данные. Это тесты короткого опустошения Kafka, не длительный soak test.

[Результаты аудита логики и сравнений](audits/configuration-logic-audit-2026-11-04.md).
