# Повторная проверка конвейера, 3 ноября 2026

Проверена установленная конфигурация после смены кодека OpenSearch. Новых изменений производственного кода в этой проверке нет. В диагностические скрипты добавлены размер запуска и интервал опроса.

## Условия и результаты

Colima ARM64, 8 vCPU / 6 GB RAM; один OpenSearch 2.17.1, heap 512 MiB; 2 primary shards, replicas=0, zstd_no_dict level 1. Буфер RAM 32 MiB, журнал Redis с бюджетом 256 MiB, два bulk workers по 5 MiB. Refresh 30s, translog async/5s и Redis AOF everysec сохранены.

Две отдельные партии по 50 000 сообщений: случайный текст 10 240 байт, средний входной JSON 10 416 байт. Предварительное накопление в Kafka, затем чтение всей партии. Использовано автоматическое создание индексов приложением; фактические настройки проверены. Полное сообщение сохраняется в payload_json, однако поисковое поле message ограничено первыми 500 байтами плюс маркер усечения. Это не тест полнотекстовой индексации всех 10 КиБ.

Это короткие диагностические запуски, по одному на конфигурацию. Разброс окружения, AOF rewrite и стоимость профилирования не исключены. Результаты не доказывают, что восемь workers всегда медленнее, но не дают оснований включать их по умолчанию. Сохранено четыре. Скорость короткого опустошения Kafka нельзя считать гарантированной длительной производительностью. Видимость в поиске отделена от подтверждения bulk и зависит от refresh.

## Куда уходит время

Суммы диагностических стадий за окно запуска:

| Стадия | 4 workers | 8 workers |
|---|---:|---:|
| Decode JSON | 1,424 с | 1,335 с |
| Prepare/нормализация | 1,091 с | 1,157 с |
| Приём в журнал, всего | 2,884 с | 3,342 с |
| Внутри него storeFresh | 2,337 с | 2,797 с |
| Ожидание блокировки приёма | 0,043 с | 0,061 с |
| Запись в OpenSearch, стадия publisher | 4,641 с | 5,413 с |
| Подтверждение публикации | 0,764 с | 0,890 с |

Стадии приёма внутри Kafka-пакета последовательны; publisher работает параллельно. Суммировать все строки как общее время нельзя. Окно логов шире фазы опустошения Kafka и содержит небольшое число фоновых сообщений; особенно нельзя интерпретировать сумму kafka_poll как точное время ожидания этой партии. Опрос запрошен каждые 0,25 с, фактическая частота ниже из-за времени API.

Redis server commandstats: EXEC занял суммарно 0,387 / 0,556 с, при клиентском storeFresh 2,337 / 2,797 с. EXEC включает вложенные HSET: эти времена нельзя складывать. storeFresh также включает размещение в PostgreSQL, построение клиентского pipeline, передачу полного тела, ожидания и чтение ответов. Поэтому называть весь storeFresh временем работы Redis или доказанным насыщением Redis CPU неверно. В обоих запусках произошёл один AOF rewrite; его причинный вклад отдельно не измерен.

Docker-снимки во время нагрузки показывают API примерно 1,0–1,7 ядра, контейнер Redis 1,3–1,6 (включая фоновые процессы), OpenSearch 1,5–2,2; PostgreSQL значительно ниже. Выборка редкая, это не интегральные средние. Redis RAM доходила примерно до 1,73 GiB, API до 272 MiB, OpenSearch около 1,4 GiB. Память Redis содержит метаданные множества прежних тестов.

Вывод: после устранения прежней дорогой компрессии OpenSearch конвейер стал более сбалансированным. Приём/JSON/журнал уже сопоставимы с публикацией, а накопление очереди ограничено несколькими тысячами. Единственный жёсткий предел CPU, диска или OpenSearch этим измерением не установлен. Запись OpenSearch по-прежнему существенна; объявлять её полностью устранённым ограничением нельзя.

Следующая предметная оптимизация: CPU/alloc-профиль Go на фазе decode/prepare и отдельный замер построения pipeline, размещения PostgreSQL, Redis round-trip и разбора ответов. Затем уменьшение повторной обработки полного JSON и последовательных ожиданий между Kafka и журналом с сохранением дедупликации и ACK после записи. Простое увеличение workers не подтвердило пользу. Переписывать журнал или ослаблять сохранность по этим данным оснований нет.

## Проверка исправности и восстановления

- `go test -count=1 ./...` с тестовой PostgreSQL: PASS.
- `go vet ./...`: PASS.
- `go test -race -count=1 ./internal/httpapi ./internal/search ./internal/redisingest ./internal/kafkainput`: PASS.
- OpenSearch приостановлен; принято 4 000 сообщений по 10 КиБ за 1,379 с, публикация 0, очередь 4 000.
- Штатный restart Redis сохранил тела выбранных сообщений; после возобновления OpenSearch опубликованы и найдены ровно 4 000.
- Полные значения четырёх контрольных payload проверены; повторная отправка дала три duplicate; конфликт содержимого отклонён 409, запись оператором отклонена 403.
- Это проверка штатного перезапуска и остановки процесса публикации, не внезапного отключения питания.

По завершении: Kafka работает, lag=0; pending=0; все пять основных контейнеров запущены без pause; OpenSearch green. Диагностика отключена, workers=4. Оператор видит только Billing. Диск занят на 81%, доступно 18,1 GB; индексы 43,7 GB и 120 shards с накопленными тестовыми данными. Это ограничивает объём дальнейших экспериментов, но не является доказанной причиной текущей скорости. Исторические данные не удалялись.
