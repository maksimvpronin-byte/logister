# Аудит логики и конфигураций, 4 ноября 2026

Проверены приём HTTP/Kafka, нормализация, дедупликация, Redis-журнал, публикация,
владение очередью, ротация и параметры параллелизма. Сравнение: 16 прогонов по
100 000 сообщений с полным индексируемым текстом 5 120 байт, плюс два сценария
восстановления по 4 000 сообщений с текстом 10 240 байт. Всего проверены
1 608 000 синтетических сообщений. После успешной проверки их данные удалены.

## Результат

Два шарда и два bulk workers на этом стенде полезны. Четыре normalizer workers
и RAM-предвыборка по отдельности не показали уверенного преимущества для простых
сообщений 5 КиБ. Однако их совместное отключение в исправленной сборке уменьшило
производительность примерно на 9%. Все рабочие значения по умолчанию сохранены:
INGEST_WORKERS=4, BULK_WORKERS=2, OUTPUT_BUFFER_BYTES=33554432,
OPENSEARCH_SHARDS=2 для новых индексов. Изменение числа шардов не затрагивало
существующие обычные индексы.

Внесены три исправления логики, установлены в API:

1. **Нулевая настройка буфера.** Раньше общий envInt отвергал 0 и незаметно
   подставлял 32 МиБ. Теперь OUTPUT_BUFFER_BYTES=0 явно выбирает последовательную
   публикацию. Обязательный лимит журнала 256 МиБ этим не отключается.
2. **Чтение сверх бюджета.** Publisher раньше получал HGETALL для всех 1 000
   кандидатов, затем обрезал порцию по байтам. При крупных событиях временная
   загрузка тел существенно превышала бюджет окна. Теперь сначала получаются
   длины, затем загружается только выбранный префикс. Одиночный oversized event
   по-прежнему допускается для прогресса; бюджет окон не является лимитом RSS.
3. **Устаревший приёмщик после потери блокировки.** Раньше SET NX с TTL
   сериализовал обычные записи, но владение не проверялось атомарно при EXEC.
   Теперь WATCH/проверка владельца защищает запись тел, очереди, счётчиков и
   batch receipt в одной транзакции. Смена/истечение блокировки до EXEC прерывает
   её. Удаление указателя активного поколения при ротации защищено аналогично.
   Нормализация старого Kafka-хеша использует compare-and-set, освобождение
   intake-блокировки ограничено таймаутом.

Это исправления корректности, а не основание заявлять ускорение: контрольные
замеры до и после пересекаются по скорости.

## Первая матрица, исходная сборка

Два круга в прямом и обратном порядке. По одному параметру менялось относительно
baseline, кроме явно комбинированного minimal. Во всех строках два запуска,
100 000 сообщений в каждом; поиск нашёл ровно 100 000, ошибок bulk нет.

| Конфигурация | Первый запуск, логов/с | Второй запуск | Скорость по суммарному времени |
|---|---:|---:|---:|
| Baseline: 4 normalizers, 2 bulk, RAM 32 МиБ, 2 shards | 12 481 | 13 325 | 12 889 |
| Последовательная публикация, остальные baseline | 13 061 | 12 346 | 12 694 |
| Один normalizer, остальные baseline | 13 908 | 13 385 | 13 642 |
| Один bulk worker, остальные baseline | 11 332 | 10 652 | 10 981 |

| Minimal: 1 normalizer, 1 bulk, без RAM-предвыборки, 1 shard | 7 930 | 7 801 | 7 865 |

В исходной сборке для последовательной публикации применялось значение
OUTPUT_BUFFER_BYTES=1: оно помещает меньше двух окон. Это обход старой ошибки
разбора нуля, не буквальный одно-байтовый лимит документов.

Один normalizer снижал максимальную наблюдавшуюся очередь до 7 717–8 775 против
24 868–24 931 в baseline. По этой нагрузке intake не требовал четырёх workers,
но небольшой разброс EPS не доказывает преимущество одного worker для сложной
маршрутизации или другого состава сообщений.

## Контроль исправленной сборки

ABBA: baseline / lean / lean / baseline. Lean: INGEST_WORKERS=1,
OUTPUT_BUFFER_BYTES=0; два bulk workers и два шарда сохранены.

| Конфигурация | Два запуска, логов/с | По суммарному времени |
|---|---:|---:|
| Baseline | 13 295 / 13 380 | 13 337 |
| Lean | 11 668 / 12 555 | 12 095 |

Все четыре раза найдены ровно 100 000 сообщений, ошибки bulk=0, три образца
индексированного message в каждом прогоне имеют длину ровно 5 120 байт.
Наблюдавшиеся снимки памяти контейнера API: максимум около 249 МиБ в baseline,
187 МиБ в lean. Снимки редкие, не являются точным измерением пикового RSS.
Экономия памяти у lean сопровождается снижением EPS, поэтому настройки по
умолчанию не менялись. Пользу отдельных упрощений нельзя складывать арифметически.

записи оператором=403. Это не моделирование внезапного отключения питания.

## Где остаётся сложность и что делать дальше

**P1 — бессрочные receipt-ключи.** После публикации body удаляется, ID/hash/target/
stream остаются без TTL. Retention индексов не очищает эти записи. Это линейный
рост памяти с числом когда-либо принятых событий; ранее на тестовых данных уже
наблюдалось около 1,5 ГиБ Redis. Нужна явная политика срока дедупликации и
очистки старых квитанций с учётом Kafka replay и смены поколений индексов.
Просто добавить короткий TTL нельзя без изменения обещаний повторной доставки.

**P1 — нет DLQ для постоянной ошибки сообщения.** decodeKafka/acceptKafka
возвращает ошибку партии; consumer не подтверждает offsets и повторяет её.
Некорректный JSON либо явный адрес несуществующего/удалённого потока способны
заблокировать продвижение чтения. Защита от потери данных работает, но нужна
политика DLQ/quarantine с подтверждением только после сохранения плохой записи.
В рабочий Kafka-топик намеренно не отправлялись неисправимые сообщения.

**Архитектурное перекрытие Kafka и Redis.** Сейчас Kafka буферизует вход,
Redis даёт общий журнал HTTP/Kafka, дедупликацию и счётчики, PostgreSQL хранит
настройки/роли/каталог, OpenSearch обслуживает поиск. Это объясняет функции
компонентов, но две долговременные очереди увеличивают число состояний отказа.
Унификация HTTP -> Kafka -> обработчик -> OpenSearch может убрать один журнал,
однако требует заново определить ACK, повторы, счётчики и дедупликацию. Здесь
такой обход не включался, поскольку он меняет проверяемые гарантии.

**Служебный код.** Остались старый PostgreSQL-путь совместимости и диагностический
kafka-direct-bench в API image, а также набор частично дублирующихся стендовых
скриптов. Их можно вынести в tooling/legacy после проверки миграций. Это прежде
всего размер образа и сопровождение; текущая матрица не доказала их влияние на EPS.

Не подтверждено, что цепочка JSON -> Redis -> OpenSearch имеет единственный
жёсткий предел CPU/диска во всех режимах. Не проверены длительное накопление
receipt-ключей, несколько живых API-инстансов, отказ брокера/диска, power loss,
много одновременно активных потоков и сложные production rules. Это отдельные
следующие проверки, а не основания объявлять систему готовой к HA.

## Условия, ограничения, итог

Colima ARM64 8 vCPU / 6 GB, один OpenSearch с heap 512 MiB, zstd_no_dict/1,
replicas=0, refresh=30s; журнал 256 МиБ, publish window 10 МиБ, bulk 5 МиБ.
Входной текст — случайный hex 5 120 байт, JSON с метаданными около 5 296 байт.
Это синтетика, не набор реальных stack traces. Прогоны короткие: время доставки
около 7–13 с, видимость проверялась отдельно после естественного refresh.
Два повтора и обратный порядок уменьшают, но не устраняют влияние GC, AOF rewrite,
кэшей и фоновой нагрузки. Статистическая значимость небольших различий не установлена.

16 тестовых индексов физически удалены, их квитанции очищены, отчёты сохранены.
Оба recovery-потока также очищены. В конце — пять обычных потоков, оператор видит
только billing; Kafka running/lag=0, OpenSearch green, 31 shard. Во время обычной
генерации pending может кратковременно расти; зафиксирован итоговый снимок pending=0.
