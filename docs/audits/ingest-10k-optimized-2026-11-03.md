# Ускорение обработки сообщений 10 КиБ — реализация и проверка

Дата: 3 ноября 2026. Стенд: Colima ARM64, 8 vCPU, 6 ГиБ RAM, общие диск и CPU
для Kafka, API, Redis, PostgreSQL и OpenSearch. Базовые замеры и обоснование:
[исходный отчёт](ingest-10k-performance-2026-11-03.md).

## Что установлено

- Старый hash совместимости вычисляется лениво, только для повтора ID версии 1.
  Исходный проверенный JSON переиспользуется для сохранения payload. Канонический
  hash и проверка конфликтов ID сохранены, числовые значения остаются json.Number.
- Декодирование Kafka и подготовка событий работают с четырьмя обработчиками.
  Результат остаётся в порядке входа; сохранение начинается после валидации всего
  пакета. Kafka offset подтверждается только после сохранения всех его частей.
- Подготовка индекса кешируется на 5 минут, до 512 записей, с singleflight.
  Повторные HEAD/mapping на каждый bulk убраны; при 404/удалении кеш сбрасывается.
- Публикация разбивается по байтам, до двух bulk одновременно, с ожиданием всех
  ответов. Очередь удаляется только после успешной публикации всего выбранного
  диапазона. Частичный успех повторяется с прежними ID.
- У publisher возобновляемая аренда на 30 секунд, продление каждые 10 секунд.
  Lua ACK проверяет владельца, префикс очереди, наличие тел и счётчики до изменений.
  Устаревший владелец не может удалить новую работу. Счётчики уменьшаются
  агрегированно, префикс убирается одним LTRIM вместо LREM на каждую запись.
- Проверка дублей читает HMGET hash/version/stream; тело требуется только для
  редкой совместимости старого Kafka envelope.
- Введён бюджет ожидающих тел Redis 256 МиБ. При заполнении приём ждёт освобождения
  до 30 секунд; Kafka остаётся источником backlog. Повторы уже принятых ID допустимы
  при заполнении. Один oversized batch допускается в пустую очередь для прогресса.
  Это бюджет тел, **не всей RAM Redis**: hash/ID и прочие метаданные остаются отдельно.
- Непустые пакеты publisher обрабатывает без прежней паузы 200 мс, даже если
  byte-limit уменьшил число записей ниже 1000.

Параллельных Kafka consumer по разделам пока нет: получение и подтверждение poll
последовательны, распараллелены этапы без общего изменяемого состояния этапы внутри пакета. Это сохраняет прежнюю
семантику порядка и не требует ослаблять глобальную блокировку Redis Accept.
Политика удаления исторических ID/hash не добавлена: TTL без согласованного окна
повторов допускает дубли. Пулы буферов пока не понадобились.

## Рабочие параметры

| Переменная | Значение | Назначение |
|---|---:|---|
| INGEST_WORKERS | 4 | Декодирование и нормализация |
| KAFKA_BATCH_RECORDS | 1000 | Верхняя граница poll |
| KAFKA_BATCH_BYTES | 10485760 | Разбиение poll перед приёмом |
| PUBLISH_BATCH_BYTES | 10485760 | Бюджет документов одной публикации |
| INGEST_QUEUE_MAX_BYTES | 268435456 | Бюджет ожидающих тел Redis |
| BULK_MAX_BYTES | 5242880 | Целевой размер bulk с оценкой метаданных |
| BULK_WORKERS | 2 | Максимум bulk одновременно |

Бюджеты допускают одно сообщение сверх лимита, чтобы оно могло продвинуться.
Kafka fetch имеет собственные лимиты 32/16 МиБ; ожидание fetch — 100 мс.
Параметры доступны через env API и передаются docker-compose.yml.

## Нагрузка и сравнение

Каждый большой прогон: 100 000 сообщений, текст ровно 10 240 байт случайных
hex-данных; средний полный входной JSON 10 415,78 байта. Сначала полностью
наполняли Kafka, затем включали чтение. Фоновый генератор продолжал работать.
Состояние снималось примерно раз в секунду; разрешение окончания — около 1 секунды.
Редкий поиск раз в 5 секунд не является многопользовательской поисковой нагрузкой.

| Вариант | Доставка 100 000 | Лог/с | Входной JSON, МиБ/с | Поиск: все 100 000 |
|---|---:|---:|---:|---:|
| До изменений, прогон 1 | 17,25 с | 5 796 | 57,6 | 30,59 с |
| До изменений, прогон 2 | 17,34 с | 5 766 | 57,3 | 30,74 с |
| Оптимизации, до бюджета очереди | 12,31 с | 8 125 | 80,7 | 30,81 с |
| Итоговые настройки: 2 bulk × 5 МиБ | 11,26 с | 8 882 | 88,2 | 30,86 с |
| 1 bulk × 5 МиБ | 16,36 с | 6 113 | 60,7 | 30,90 с |
| 4 bulk × 2 МиБ | 11,50 с | 8 694 | 86,4 | 31,06 с |

Оставлены **2 bulk по 5 МиБ**: дополнительная параллельность выигрыша не показала.
Против второго baseline: +54% EPS, время доставки меньше на 35%. Разница между
двумя и четырьмя bulk мала относительно точности и вариативности короткого теста;
это выбор консервативной настройки, не доказательство универсального оптимума.
Во всех четырёх оптимизированных прогонах доставлены и точно найдены **400 000**
записей, ошибок consumer/мониторинга нет. В итоговом прогоне наблюдалась очередь
Redis до 23 621 записи; бюджет ограничивает ускоренный приём при более медленной записи.

Доставка означает ответ OpenSearch, а не поисковую видимость. Refresh 30 секунд
оставлен прежним. Полный payload сохранён, но текстовое поле message индексирует
только первые 500 байт; payload_json не индексируется. Это **не измерение полного
текстового поиска по всем 10 КиБ**. Это короткие backlog-тесты, не длительная
гарантия производительности и не измерение p95/p99 задержки каждого сообщения.

В итоговом прогоне три выборки Docker полностью попали в интервал разбора:
API в среднем 112,3% CPU, OpenSearch 183,9%, Redis 51,6%, Kafka 4,5%, PostgreSQL
0,4% (100% = одно ядро). Итого около 3,53 ядра из 8 в этих выборках. Это редкие
выборки, не интегральное потребление CPU всего теста. У OpenSearch стало больше
работы одновременно; увеличение общего числа CPU само по себе пока не требуется.
Redis передал около 1,23 ГБ входящего / 1,25 ГБ исходящего трафика, AOF переписан
один раз за интервал доставки. Журнал по-прежнему передаёт полное тело туда и обратно.

## Микробенчмарк JSON

Один и тот же последовательный BenchmarkKafkaNormalize10KiB, batch 1000,
Darwin ARM64 / Apple M5, без сетевого I/O. Это профиль хоста, не Linux-контейнера.

| Показатель | До | После |
|---|---:|---:|
| Время / batch | 126,19 мс | 49,75 мс |
| Лог/с в микротесте | 7 924 | 20 102 |
| Heap bytes / batch | 125 528 240 | 80 607 268 |
| Аллокации / batch | 156 990 | 105 006 |

Примерно 2,54× по скорости локальной подготовки и на 35,8% меньше выделенной памяти.
Это не обещание 20 тыс. EPS всей системы.

## Изолированный эксперимент Kafka → OpenSearch

Добавлены cmd/kafka-direct-bench и deploy/tests/kafka_direct_profile.py.
Они используют отдельные directbench-* топик/индекс/группу, общий декодер,
маршрутизацию и формат документа. Redis-журнал обходится. Kafka offsets
подтверждаются после bulk с **translog.durability=request** тестового индекса.
Рабочая группа и настройки обычных индексов не меняются.

Результат: 100 000 / 100 000, 10,90 с, **9 178 лог/с**, видимость 31,00 с.
Полный JSON чуть больше (10 421,78 Б) из-за имени потока. За интервал эксперимента
Redis получил лишь ~213 КБ и отдал ~61 КБ (фон/мониторинг), вместо передачи ~1 ГБ
тел туда и обратно. Это подтверждает устранение промежуточного трафика.

Результат близок к оптимизированному журналу. Семантика ACK и окружение различаются,
одного прогона недостаточно для вывода о превосходстве. Это **не готовая замена
production pipeline**: фиксированный индекс, нет его ротации, общей статистики,
журнальных receipts и проверки ID-content конфликтов. Тест использует уникальные
события; стабильные ID защищают повтор bulk от второго документа. В production
прямой режим не включён.

## Надёжность и проверки

Redis AOF everysec, OpenSearch async / sync 5s, replicas=0 оставлены прежними.
Окна потери несинхронизированных данных при аварии узла не устранены этим патчем;
чистый restart не является доказательством устойчивости к отключению питания.

Автоматические проверки:

- go test ./... с локальной тестовой PostgreSQL, go vet ./...;
- go test -race для httpapi, search, redisingest, kafkainput;
- конфликты ID, ленивый legacy hash, raw JSON и большие числа, недопустимый JSON;
- сохранение порядка byte-chunks, ошибка части пакета прекращает дальнейший приём;
- cache singleflight и восстановление после bulk 404, ограниченная параллельность;
- ошибка записи сохраняет очередь, потерявший lease владелец не ACK-ает,
  два publisher не уменьшают счётчики дважды, некорректный счётчик не удаляет тело;
- бюджет очереди приостанавливает приём и возобновляет после освобождения.

Живой сценарий ingest_optimized_faults.py приостанавливает OpenSearch, принимает
3 события с текстом по 10 240 байт, повторяет их, проверяет тела Redis, чисто
перезапускает Redis, возвращает OpenSearch и сверяет ровно 3 документа и полный
исходный текст каждого из них. Также проверяет HTTP 409 при изменённом
payload с прежним ID и запрет ingest оператору (403). Kafka pause восстанавливается.

## Воспроизведение и артефакты

```sh
python3 deploy/tests/kafka_profile.py --count 100000 --bytes 10240
python3 deploy/tests/kafka_tune_matrix.py
python3 deploy/tests/kafka_direct_profile.py --count 100000 --bytes 10240
python3 deploy/tests/ingest_optimized_faults.py
```

Запускать последовательно на локальном LDAP-стенде, без одновременного изменения
конфигурации. Матрица пересоздаёт только API и восстанавливает исходные env.
Fault-сценарий кратковременно останавливает OpenSearch и перезапускает Redis.
Тестовые нагрузочные потоки и данные остаются для проверки; fault-поток архивируется.

Сырые отчёты в graphify-out:

- kafka-profile/20261103T182835Z-02f3e9 — первый оптимизированный;
- kafka-profile/20261103T183406Z-e40660 — итоговые настройки;
- kafka-profile/20261103T183519Z-0c4b44 — 1 × 5 МиБ;
