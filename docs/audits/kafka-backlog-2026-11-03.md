# Проверка Kafka и удаления потоков — 3 ноября 2026

На локальном стенде развернута цепочка Fluent Bit → Kafka → Logister → PostgreSQL
→ OpenSearch. Kafka — один брокер 3.9.1 KRaft, 6 разделов входящего топика;
consumer внутри API, одна группа `logister`, пакеты до 200 сообщений.
Стенд Colima ARM64: 2 CPU, 6 ГБ RAM, общий диск VM 100 ГБ.

## Чистый тест накопленной очередью

Сценарий `python3 deploy/tests/kafka_backlog.py --count 250000`:

1. Создан отдельный поток `kafka-load-20261103t130429z-4a7f34`.
2. Чтение Kafka остановлено на границе пакета, дождались `running:false`.
3. Отправлены 250 000 уникальных сообщений. Текст каждого — 512 случайных
   символов; полный JSON в среднем 692 байта, суммарно 173 027 780 байт.
4. Kafka подтвердила все записи: 250 000 acknowledged, 0 failed,
   заполнение за 1,441 секунды. Локальный producer примерно 173 тыс. записей/с;
   это краткий приём брокером, не скорость индексации Logister.
5. В Kafka накопилось 250 002 непрочитанных записи с учётом фоновых логов;
   в тестовом потоке Logister приём оставался нулевым.
6. API перезапущен, проверено сохранение паузы и нулевого приёма тестового потока.
7. Чтение возобновлено. Через 96,299 секунды приняты и доставлены все 250 000,
   PostgreSQL pending = 0 и Kafka lag = 0 на завершающем измерении.
8. В поиске точно 250 000 документов. Ошибок consumer на чистом прогоне нет.

Средняя скорость полного разбора с момента возобновления, включая вступление
в группу, доставку и интервал мониторинга: **2 596,1 лог/с**. Дискретность
мониторинга около секунды; завершение приёма и доставки попало в один замер.
Максимальная наблюдённая очередь PostgreSQL — 800 сообщений. Обычный генератор,
Fluent Bit и периодический мониторинг продолжали работать; отдельной постоянной
поисковой нагрузки в этом Kafka-прогоне нет (параллельно проверялся интерфейс).
Это краткий тест backlog, а не подтверждение работы сутками при таком потоке.

## Совместимость перехода с HTTP

Первый тест выявил конфликт дедупликации: Kafka-выход Fluent Bit автоматически
добавлял числовую служебную метку `@timestamp`, отличающую исходный payload
от ранее принятых HTTP-сообщений. Consumer остановился, не подтвердив ошибочный
пакет. Накопленные Kafka records сохранились.

Исправлено отделение служебной метки `__logister_kafka_timestamp` от приложения.
Для первоначального Kafka-конфига добавлена узкая совместимость: проверяются
сохранённый исходный payload, старый и нормализованный хеши. Проверка реального
изменения содержимого остаётся строгой. Исправление покрыто тестами, включая
вложенный JSON из Fluent Bit `log`. После исправления первая очередь также
полностью разобрана: 250 000 принятых и доставленных событий, pending = 0.
Первый прогон с паузой для исправления не используется для оценки скорости.

## Удаление потоков

Проверено API и браузером:

- Администратор удаляет поток после ввода его идентификатора.
- Поток скрывается из списка, маршрутизации и поиска; явная отправка отклоняется.
- Восстановление возвращает поток и доступ к сохранённым документам.
- Политика хранения продолжает действовать; окончательная очистка по retention
  не отменяется обратимым удалением потока.
- Старые поисковые курсоры после скрытия недействительны.
- Приём со старым снимком маршрутизации дополнительно проверяет строку потока.
- Системный `all` защищён на сервере, оператору операции запрещены.
- Оператор по-прежнему видит статистику только Billing; Kafka-панель ему запрещена.
