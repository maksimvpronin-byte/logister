# Где ограничена обработка 10-КиБ сообщений и что исправлено

Дата: 3 ноября 2026. Стенд Colima ARM64, 8 vCPU, около 6 ГиБ RAM,
один OpenSearch с heap 512 МиБ. Цепочка Kafka → API → Redis → OpenSearch.

## Итог

Подтверждено главное ограничение данного сценария: **ожидание индексации в
OpenSearch при одном primary shard на активный индекс**. Гипотеза о том, что
сейчас главным тормозом является глобальная блокировка Redis, замерами не
подтвердилась. Переписывать механизм блокировки ради этого теста не потребовалось.

Исправление установлено: приложение создаёт новые managed-индексы с **двумя
primary shard**. Пять рабочих потоков all, billing, payments, system, web-access
переведены через штатную ротацию на новые поколения. Документы прежних поколений
сохранились, чтение идёт через прежний alias, UUID потоков и роли не менялись.

Финальные прогоны: **10 822 и 10 840 лог/с** при заранее созданном индексе,
**10 557 лог/с** при создании индекса самим приложением во время приёма.
Все три раза точно найдены 100 000 / 100 000 документов.

Это устранение конкретного ограничения одним шардом, а не утверждение, что
в конвейере исчезли все ограничения производительности или длинные задержки.

## Как локализовали

Добавлена выключенная по умолчанию диагностика INGEST_PROFILE_STAGES=true:

- Kafka poll и commit;
- разбор JSON и подготовка/маршрутизация;
- полный приём Redis, число повторов ожидания бюджета очереди;
- получение блокировки, дедупликация и сохранение Redis;
- publisher: аренда, чтение очереди, ожидание публикации, ACK.

Время bulk отдельно снималось прежним INGEST_PROFILE_BULK=true. Логи содержат
только этапы, число документов и длительности, без payload и паролей.
Из общей статистики выбирались пакеты от 32 документов, чтобы убрать одиночные
фоновые события; часть фоновых событий всё равно может попасть в большие пакеты.

Суммы wall-time этапов исходного замера на 100 000 сообщений:

| Измерение | 1 шард | 2 шарда, без изменения алгоритма |
|---|---:|---:|
| Время доставки по опросу | 13,62 с | 10,25 с |
| Publisher всего | 13,17 с | 9,07 с |
| Из него ожидание записи OpenSearch | **11,30 с** | **7,45 с** |
| Чтение очереди publisher | 1,28 с | 1,14 с |
| ACK Redis | 0,56 с | 0,43 с |
| Получение аренды publisher | 0,014 с | 0,036 с |
| Получение блокировки приёма Redis | **0,158 с** | **0,050 с** |
| Kafka commit | 0,122 с | 0,091 с |
| Разбор JSON | 1,92 с | 1,84 с |
| Подготовка/маршрутизация | 1,57 с | 1,36 с |
| Сохранение новых сообщений Redis | 3,23 с | 2,29 с |

Ожидание записи занимает **82–86% времени publisher**. При одном шарде очередь
достигла бюджета, что вызвало 181 повтор ожидания приёма. При двух шардах в парном
замере таких ожиданий не было. Это ожидание освобождения очереди — следствие
более медленной публикации, его нельзя выдавать за время блокировки Redis.

Этапы intake и publisher выполняются параллельно. Строки таблицы нельзя складывать
как время всего теста; accept_total включает вложенные этапы и ожидание бюджета.
Сумма documents у accept_once может включать повторные попытки одного пакета.

В предыдущей серии 1 → 2 → 4 → 4 → 2 → 1 суммарная скорость на двух шардах была
10 239 против 8 473 лог/с на одном, прирост около 21%.
[Подробности контрольной серии](ingest-shards-10k-2026-11-03.md).
По двум сериям есть воспроизводимое улучшение при двух шардах. Разницу между
единичным исходным замером 7343 и последним 10840 нельзя считать гарантированным
приростом 48%: состояние VM, фон и точность коротких замеров меняются.

## Дополнительные гипотезы

**Хвост третьего bulk.** Проверено ограничение окна publisher одной волной
bulk-запросов, с общей оценкой NDJSON-объёма. Два прогона на двух шардах дали
9708 и 9713 лог/с против 9758 в исходном двухшардовом варианте. Устойчивого
ускорения нет. Экспериментальный алгоритм удалён; в финальной сборке исходная
разбивка publisher и прежний fenced ACK.

**Redis AOF/fork.** На время измерений включён latency monitor с порогом 5 мс,
затем его исходное значение восстановлено. В журнале наблюдались fork и AOF write
задержки в единицы/десятки миллисекунд. Значения LATENCY LATEST могут сохраняться
между прогонами: timestamp и lifetime max не равны показателям только текущего
интервала. Они не доказывают причину отдельных bulk по 0,5 секунды.
AOF everysec не отключался, режим надёжности не ослаблялся.

**Диск, GC и PostgreSQL.** Предыдущая серия зафиксировала busy виртуального диска
около 17–21%, средний read/write await около 0,8–1,2 мс, old GC отсутствовал,
merge throttle=0, PostgreSQL почти не загружен. В этом исследовании также сохранены
node stats, diskstats, PSI, cgroup I/O и Redis INFO. Данных за длительное насыщение
физического SSD хоста или блокировку PostgreSQL как основную причину нет.

## Изменения кода и рабочего стенда

- OPENSEARCH_SHARDS=2 в Config и docker-compose; допустимое значение ограничено
  диапазоном 1–16. Client.ConfigureShards влияет только на создание нового
  stream-индекса. Существующие физические индексы не перестраиваются.
- main передаёт настройку клиенту OpenSearch. Mapping и read alias сохраняются.
- Штатным POST /api/streams/{name}/rotate закрыты прежние активные поколения
  пяти рабочих потоков. Проверено создание поколения 000002 с двумя шардами
  и доставка контрольного сообщения в каждый поток.
- После ротации числа документов во всех прежних индексах остались прежними:
  all — 24 147, billing — 15, payments — 13, system — 6095, web-access — 6070.
  Сырые снимки: graphify-out/ingest-research/deployment.json.
- Диагностические флаги в конце выключены, исходный порог Redis latency monitor
  восстановлен, Kafka работает и очередь пуста.

Гарантии ACK, дедупликация, привязка старого ID к прежнему индексу, LDAP и роли
сохранены. Старые данные продолжают жить по прежним retention-политикам.

## Контроль финальной сборки

| Прогон | Создание индекса | Доставка 100 000 | Лог/с | Поиск |
|---|---|---:|---:|---:|
| 20261103T192005Z-169845 | Заранее, 2 шарда | 9,24 с | 10 822 | 100 000 |
| 20261103T192042Z-4321e6 | Заранее, 2 шарда | 9,23 с | 10 840 | 100 000 |
| 20261103T192152Z-4ebb23 | Приложением, 2 шарда | 9,47 с | 10 557 | 100 000 |

В каждом сообщении 10 240 байт случайного hex-текста; средний JSON 10 415,78 байта.
Окончание доставки определяется примерно секундным опросом. Редкий поиск не
является тестом многопользовательской поисковой нагрузки. Первый auto-index
прогон включает создание индекса; две предыдущие строки этого не включают.

Все 300 000 контрольных сообщений финальной сборки приняты, доставлены и точно
найдены, без ошибок bulk/consumer/мониторинга. Всего в текущем исследовании
900 000 сообщений, включая исходные и экспериментальные прогоны.

Полный payload сохраняется, но текстовое message индексирует первые 500 байт
с маркером «…». Это не полнотекстовая индексация всего 10-КиБ сообщения.
Refresh 30s, translog async / sync 5s, replicas=0 и Redis AOF everysec прежние.

Пройдены:

- go test -count=1 ./... с локальной тестовой PostgreSQL и go vet ./...;
- go test -race -count=1 для httpapi, redisingest, search, kafkainput;
- Docker build со всеми Go-тестами;
- новый тест: shards=2 задаётся при создании, настройки существующего индекса
  не переписываются;
- живой fault-тест после установки: пауза OpenSearch, приём 3 × 10 КиБ,
  повтор как дубли, чистый restart Redis, сохранность тел, доставка ровно 3
  документов и точное совпадение полного текста; конфликт ID даёт 409,
  ingest оператору запрещён с 403.

Чистый restart и временная пауза не доказывают устойчивость к отключению питания.
Окна несинхронизированных данных прежних режимов журналов остаются отдельным вопросом.

## Артефакты и воспроизведение

- graphify-out/ingest-research/20261103T191201Z-baseline — исходные этапы 1/2;
- graphify-out/ingest-research/20261103T191602Z-fixed — эксперимент с окном,
  удалённый из финальной реализации;
- graphify-out/ingest-research/20261103T191959Z-deployed — контроль финальной сборки;
- graphify-out/ingest-research/20261103T192146Z-auto-created — автоматическое создание;
- graphify-out/ingest-research/deployment.json, final-checks.json и faults.json.

Каждый report.json указывает на подробный Kafka report, bulk.json и resources.json.
Длительности этапов сохраняются отдельно в *-stages.json.

```sh
python3 deploy/tests/ingest_research.py --label check --shards 1 2
python3 deploy/tests/ingest_research.py --label auto --shards 2 --auto-index
python3 deploy/tests/ingest_optimized_faults.py
```

Сценарии временно пересоздают API с диагностикой, сохраняют паузу Kafka и настройки
мониторинга, затем восстанавливают их. Запускать последовательно на локальном
LDAP-стенде, без других нагрузочных тестов в это же время.

## Первичные источники

Методика контролируемых изменений, подбора bulk, проверки статистики flush и
компромисса refresh опирается на [документацию OpenSearch по indexing speed](https://docs.opensearch.org/latest/tuning-your-cluster/performance-tuning/indexing-speed/).
Её показатели чужих benchmark не переносились на наш стенд.

Для разделения задержек сети, команд и фоновой работы Redis использованы
[Redis latency diagnosis](https://redis.io/docs/latest/management/optimization/latency/)
и [Redis pipelining](https://redis.io/docs/latest/develop/using-commands/pipelining/).
В нашем коде pipeline уже есть; само добавление ещё одной блокировки или очереди
не обосновывается этими рекомендациями.
