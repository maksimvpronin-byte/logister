# Ресурсы физического хоста и конкуренция за метаданные

Один Mac с 10 CPU и 16 ГиБ RAM. Три Colima VM имеют суммарно 9 vCPU и 10 ГиБ назначенной памяти. До прогона macOS уже использовала около 7,66 ГиБ swap. На хосте работали другие сервисы, их не останавливали. Свободное место на диске проверено перед каждым циклом. Термальных предупреждений в исходном снимке не было.

Во время тестов каждые четыре секунды сохранялись метрики macOS, Linux CPU/PSI и памяти, дисков ВМ и CPU/RAM контейнеров. Снимки только из нагрузочного интервала. Swap — прирост накопительных счётчиков macOS между первым и последним снимком, поэтому числа приблизительны. Стенд использовал три реплики Kafka, три процесса API и одну реплику OpenSearch на каждый первичный шард. Каждое событие имело сообщение 5 КиБ.

| Исходная сборка, по 100 000 событий | Событий/с | Время, с | Swap-out macOS, МиБ |
|---|---:|---:|---:|
| Штатная конфигурация, первый | 1 725 | 57,98 | 3 232 |
| Один bulk worker вместо двух на API | 1 969 | 50,78 | 1 957 |
| Один работник подготовки вместо двух на API | 2 030 | 49,27 | 2 134 |
| Штатная конфигурация, повтор | 2 186 | 45,75 | 1 297 |

В первом прогоне медиана idle физического CPU составляла 1,7%, минимум 0,35%. ВМ были заняты по CPU на 81–94%, у OpenSearch медиана загрузки на узел 136–171% в метрике Docker, где 100% — одно ядро. У API медианы 20–28%. На двух меньших ВМ минимум доступной памяти составил 361–390 МиБ, их Linux swap-счётчики не росли. Максимальный IO PSI full составлял 1,36%. Подкачка и ограничение CPU видны прежде всего на физическом хосте. Уменьшение числа работников API попало в разброс двух штатных контролей.

## Изменение транзакций подтверждения

Подтверждение переводит записи журнала в состояние published и добавляет отдельную запись по пачке и индексу в той же транзакции majority. Резервирование по-прежнему обновляет счётчик поколения для ротации. Путь подтверждения проверяет каталог, но не переписывает общую запись поколения. Опубликованное число вычисляется из старого счётчика и новых подтверждений, поэтому старые данные читаются. Для удаления проверяется эффективный pending и время последней записи с учётом нового журнала. Публикация в OpenSearch и фиксация Kafka offset остались в прежнем порядке.

Дополнительная запись MongoDB на пачку и индекс. Пока данные сохраняются, записи подтверждений нужны для итоговых счётчиков. Тест с живой MongoDB проверил повтор, ротацию, параллельное подтверждение и интервал защиты индекса после публикации.

## Сопоставимый одиночный прогон

На исходной сборке одиночный стенд записал 100 000 событий за 17,48 с, 5 722 событий/с. В пяти нагрузочных снимках медиана idle macOS составила 49,6%, новых выгрузок в swap не было. Объём чтения из swap составил 53 МиБ. На одном экземпляре хранилась одна копия данных. Этот тест показывает разницу в загрузке физической машины при запуске всего кластера, но меняет также число копий.

## Изоляция конкуренции при подтверждении

| По 50 000 событий | Событий/с | Конфликты MongoDB | Успешные транзакции |
|---|---:|---:|---:|
| Старый код, начало пары | 1 724 | 51 | 112 |
| Прототип без записи в общую строку поколения, первый | 2 687 | 30 | 112 |
| Прототип без записи в общую строку поколения, второй | 2 524 | 14 | 114 |
| Старый код, конец пары | 2 072 | 64 | 118 |

115 против 44 конфликтов при 230 против 226 успешно завершённых транзакций. По времени всей пары скорость составила 1 882 против 2 603 событий/с. В новом варианте macOS также меньше подкачивала память, поэтому прирост событий/с относится к этим прогонам целиком. Конфликты резервирования остаются.

Финальная версия накапливает подтверждения в одном документе на процесс API и индекс, а не в отдельном документе на каждую пачку. Старый формат счётчика сохраняет консервативный остаток. Новая версия вычитает подтверждения из отдельных записей. При откате старая сборка может завышать pending и откладывать удаление поколений, обработанных новой версией.

Финальный кластер записал 100 000 событий за 54,65 с, 1 830 событий/с. Подтверждения всех 100 000 событий уместились в шести счётчиках, три процесса и два индекса. MongoDB зарегистрировала 30 конфликтов при 234 успешных транзакциях. В исходных прогонах того же объёма было 56 и 88 конфликтов при 210 и 218 успешных транзакциях. Медиана idle хоста 1,94%, swap-out около 1 854 МиБ. Сквозная скорость осталась в диапазоне двух штатных прогонов.

Ограничение стенда зарегистрировано. Три ВМ используют общий физический CPU и память, под нагрузкой хост почти не имеет свободного CPU и активно выгружает страницы. Эти данные характеризуют ёмкость данного стенда. Для проверки горизонтального масштабирования нужна серия на независимых физических ресурсах при одинаковых гарантиях записи. При повторных замерах на этом стенде фиксировать idle и прирост swap до вывода о скорости приложения.

Штатные лимиты работников оставлены. Проверенный образ установлен на трёх узлах под logister-api:local. Все тестовые данные удалены, штатные индексы сверены, стенд остановлен. Прошли тест реальной MongoDB с race detector, полный Go test при сборке, go vet и git diff --check.

Сырые замеры, сценарии и логи находятся в `graphify-out/host-resource-audit`.
