# Полная индексация сообщений, 4 ноября 2026

Изменение установлено локально: API `logister-api:local`, UI `logister-ui:local`.
Полное сообщение теперь индексируется в `message`; 500 символов ограничивают
только превью таблицы. При раскрытии доступны полный текст и исходный JSON.
Пробелы по краям поискового сообщения нормализуются, как и прежде;
`payload_json` хранится без изменения. При отсутствии текстового message
индексируется полное JSON-представление события.

## Хранение и поля

OpenSearch хранит и сжимает исходный документ; отдельной упаковки текста в
base64/gzip перед индексацией нет. Для новых индексов сохранён ранее выбранный
`zstd_no_dict`, level 1. `payload_json` имеет `index:false`.

Введены явные поля: `service`, `request_id`, `trace_id` — keyword;
`status` — long, `ip` — IP. Значения берутся из верхнего уровня события,
при отсутствии — из fields. Некорректные типы не индексируются в этих проекциях,
но остаются в исходном JSON. Произвольные JSON-свойства автоматически не
превращаются в новые поля схемы. Существующие source/host/level/facility/stream
и совместимая проекция fields сохранены. Действия меню поля поддерживают новые
метаданные, возвращаемые API. Полнотекстовый поиск использует анализатор,
а не произвольный поиск подстроки.

## Обновление истории

`reindex_full_messages.py --apply` просмотрел 46 706 документов, изменил одну
проекцию, восемь старых записей без payload_json оставил как есть. Остальные
проекции уже совпадали с полным исходным текстом (обычные короткие сообщения).
Контрольный длинный лог был создан до установки новой версии: в message было
503 байта (500 + маркер). После обновления доступен полный текст 12 625 байт,
слово в хвосте находится; ID и исходный payload сохранены.

Обновление выполняется в существующих документах через bulk update; исходный
payload, время, stream, индекс, поколения и идентификаторы не переписываются.
Во время миграции поступали новые обычные логи, поэтому итоговый count 46 728
выше исходного. Повторный dry-run: 47 030 просмотрено, 0 изменений, восемь без
payload_json. Принудительная ротация индексов для этого изменения не нужна.

## Нагрузка после изменения

Два запуска по 100 000 сообщений, случайный hex-текст 10 240 байт, предварительное
накопление в Kafka, автоматическое создание индекса, опрос раз в секунду.
Один OpenSearch, два primary shards, replicas=0, Colima 8 vCPU / 6 GB,
heap 512 MiB. Диагностика временно включена. Все 100 000 найдены в каждом
запуске, ошибок bulk нет. Второй запуск дополнительно проверил длину трёх
индексированных message: каждый ровно 10 240 байт.

| Запуск | Приём партии | Полная доставка | Сообщений/с |
|---|---:|---:|---:|
| Первый | 16,094 с | 18,204 с | 5 493 |
| Финальный образ API | 14,446 с | 15,454 с | 6 471 |

Это короткие прогоны, не гарантия длительного throughput. Ранее 12–15 тысяч
измерялись с индексируемыми 500 байтами, сравнивать их как одинаковую нагрузку
нельзя. Теперь полный текст дублируется в поисковом message и исходном payload;
до сжатия документ примерно 20–21 КиБ вместо примерно 11 КиБ, а анализируется
всё сообщение. В финальном прогоне publisher write занял суммарно около 14,15 с
(стадии работают параллельно), наблюдалось ограничение приёма по бюджету очереди.
OpenSearch израсходовал 45,37 CPU-с, отклонённых записей нет. Это основание для
дальнейшего профилирования полной индексации, без возврата к скрытому усечению.

Синтетические потоки обоих запусков, контрольной проверки и проверки восстановления
после сохранения отчётов очищены. В конце: только пять обычных потоков,
Kafka running/lag=0, pending=0, OpenSearch green, workers=4, профилирование false.
